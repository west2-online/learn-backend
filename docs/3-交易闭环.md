# learn-backend 第三轮考核：电商业务与下单闭环

## 项目描述

### 关于项目：给工作室开一家周边小店

工作室准备卖一点自己的周边：文化衫、帆布袋、徽章……商品和价格发在群里，下单靠接龙，颜色、尺码和收货地址散落在聊天记录中。每次统计订单，都像在聊天记录里考古。

这次，在上一轮项目上开发一个**工作室周边商城后端**：管理员管理商品，用户挑选商品、管理购物车并提交订单。本轮完成日常选购、下单和简单的 mock 支付；完整支付处理、库存、发货与专项优化留到下一轮。商城主题可以更换，功能范围保持一致。

本轮开发支撑商城操作的 HTTP 接口，沿用已有的账号、登录鉴权和数据库；第二轮选做了 Docker 的同学可继续复用其配置，未选做的同学按本轮运行要求补齐环境。演示使用上一轮页面或 Apifox 等接口调试工具，完整商城前端不在考核范围内。测试和异常处理继续沿用前两轮要求。

商城中有两类使用者：

- **管理员**负责整理类目、维护商品和规格、调整价格以及上下架；
- **普通用户**负责挑选商品、管理自己的收货地址和购物车，以及查看、取消自己的订单。

本轮经营一家店，完成用户、商品、购物车、订单和 mock 支付五个模块，不包含真实支付、活动、库存、发货、多商家入驻和售后系统。收货地址归入用户模块，商品浏览归入商品模块。

### 1. 用户模块：登录、权限与收货地址

沿用上一轮的注册、登录、退出和个人信息功能，补齐角色权限、双 Token 鉴权和收货地址管理。

**角色权限（RBAC）：** 区分普通用户和管理员，为角色配置接口权限。普通用户只能操作自己的数据，管理员负责商品维护和订单查询；注册默认创建普通用户。

**双 Token：** 使用 Access Token 访问接口，Refresh Token 续期；支持令牌过期、刷新和退出后的失效处理。

**收货地址：** 支持新增、查看、修改、删除地址和设置默认地址，记录收货人、联系电话和详细地址。用户可以保存多个地址，下单时选择本次使用的地址。

### 2. 商品管理：先把货摆上货架

管理员需要能够维护商品类目、商品以及商品的具体规格。

**类目管理：** 支持新增、查看和修改类目，例如“服饰”“包袋”“小物”。商品需要归入对应类目，本轮使用简单的单级类目即可。

**商品管理：** 支持新增商品、查看商品列表和详情、修改商品信息以及上架和下架。商品信息至少包含名称、介绍和所属类目。

**SKU 管理：** 一个商品可以有多个可购买的规格组合，每个组合有自己的编号、规格信息、价格和上下架状态，管理员能够新增、查看和修改这些内容。

例如，“工作室文化衫”是一个商品，“黑色 / M 码”和“白色 / L 码”是两个不同的 SKU。用户最终买到的是选定颜色和尺码的文化衫。徽章这类没有多种规格的商品，也可以只有一个默认 SKU。

### 3. 商品浏览：让用户知道自己在买什么

用户可以分页浏览已上架的商品，查看商品详情及其可选 SKU。

- 商品列表展示商品名称、类目和价格信息，并提供详情入口；
- 商品详情展示介绍、可选规格以及各规格的价格；
- 用户选择具体规格和购买数量后，可以加入购物车。

例如，用户打开文化衫详情，选择“黑色 / M 码”、数量 2，再把这两件加入购物车。只有一种规格的商品也应能够完成同样的购买操作。

### 4. 购物车：先放着，等会儿一起买

购物车用来管理用户准备购买的商品，至少支持：

- 将选定的 SKU 和数量加入购物车；
- 查看购物车中的商品名称、规格、价格和数量；
- 修改某项商品的购买数量，或将其移出购物车；
- 选择部分或全部购物车商品提交订单。

加入购物车并不代表已经下单。例如，用户放入了两件文化衫和一个徽章，可以只选择文化衫下单，徽章仍留在购物车中。完成下单后，本次已购买的购物车项应从待购列表中移除。

### 5. 提交订单：把“想买”变成一笔订单

用户从购物车选择商品和收货地址，提交前查看商品、规格、数量、金额和收货信息，确认后创建订单。结算确认作为下单流程的一部分实现。

一张订单可以包含多个 SKU。提交成功后返回订单编号和下单结果，用户能够查看这笔订单的完整内容：

- 订单编号、下单时间和订单状态；
- 每项商品的名称、规格、购买数量、单价和小计；
- 整张订单的总金额；
- 本次使用的收货人、联系电话和详细地址。

例如，用户购买两件单价 39 元的文化衫和一个单价 12 元的徽章，这笔订单包含两项商品，总金额为 90 元。用户拿到订单编号后，可以再次打开订单详情查看这次购买记录。

本轮的“下单成功”表示商城已经接收了购买请求，不代表用户已经付款或商家已经发货。

### 6. 订单查询与取消：买了什么，还能在哪里找到

用户可以查看自己的订单列表，并通过订单编号进入详情。

列表中展示订单编号、下单时间、金额和状态等概要信息；详情展示完整的商品明细与收货信息。即使一次买了多种商品，也应能看清每项买了多少、价格是多少。

用户可以取消已创建的订单，取消后仍能在订单记录中查看它，并看到对应状态。本轮订单使用待支付、已支付、已取消三种状态：创建后待支付，mock 支付成功后已支付，只有待支付订单允许取消。重复取消返回明确结果；已取消订单不能付款，已支付订单不能取消，不要求退款和待发货状态。

完成后，应能连贯地使用这家小店：管理员创建类目并上架带有不同规格的商品，用户登录、保存地址、选购商品、从购物车下单，最后查询或取消这笔订单。

管理端也能按订单编号或状态查找订单，查看商品明细、金额和收货信息。这样店主能回答“这位同学买了什么”，本轮可以核对模拟付款结果，下一轮继续完善支付与发货。

### 7. mock 支付：模拟完成一次付款

用户为自己的待支付订单发起模拟支付，选择本次模拟结果为成功或失败，并能查询支付记录。支付金额由服务端读取订单金额，不能由请求自行指定。成功时记录支付流水号、订单编号、金额、状态和时间，并把订单改为已支付；失败时保留失败记录，订单仍待支付，允许再次尝试。

同一订单只能支付成功一次。重复调用成功支付不能产生第二笔成功记录；支付和取消同时发生时，最终状态必须符合上述规则。支付记录与订单状态更新应保持一致，不能出现支付记录成功、订单仍待支付的部分结果。

这是本地模拟接口，不接真实支付平台，不要求回调、延迟通知、对账或退款；下一轮在此基础上扩展完整支付交互。

## 参考接口

下面给出一套可直接采用的接口，减少从零设计的负担。路径和字段可按项目风格调整，但功能、权限和业务规则不能省略。请求体与响应统一使用 JSON；受保护接口携带 `Authorization: Bearer <accessToken>`，刷新接口只接受 Refresh Token。

| 模块 | 方法与路径 | 主要输入与用途 | 权限 |
| --- | --- | --- | --- |
| 用户 | `POST /auth/register` | `username, password`，注册普通用户 | 公开 |
| 用户 | `POST /auth/login` | `username, password`，返回双 Token 及有效期 | 公开 |
| 用户 | `POST /auth/refresh` | `refreshToken`，换取新的双 Token | 校验刷新凭据 |
| 用户 | `POST /auth/logout` | 退出当前登录 | 已登录 |
| 用户 | `GET /users/me`、`PATCH /users/me` | 查看、修改个人信息 | 本人 |
| 用户 | `PATCH /users/me/password` | `oldPassword, newPassword`，修改密码 | 本人 |
| 地址 | `POST /addresses`、`GET /addresses` | 新增、列出自己的地址；新增传收货人、电话、详细地址 | 本人 |
| 地址 | `PATCH /addresses/{id}`、`DELETE /addresses/{id}` | 修改、删除地址 | 本人 |
| 地址 | `PUT /addresses/{id}/default` | 设置默认地址 | 本人 |
| 类目 | `GET /categories` | 查看类目 | 公开 |
| 类目 | `POST /admin/categories`、`PATCH /admin/categories/{id}` | `name`，新增、修改类目 | 管理员 |
| 商品 | `GET /products?page=1&pageSize=20`、`GET /products/{id}` | 浏览已上架商品及可售 SKU，列表返回总数 | 公开 |
| 商品 | `GET /admin/products`、`GET /admin/products/{id}` | 查看商品，包含未上架商品 | 管理员 |
| 商品 | `POST /admin/products`、`PATCH /admin/products/{id}` | `name, description, categoryId`，新增、修改商品 | 管理员 |
| 商品 | `PATCH /admin/products/{id}/status` | `status`，上架或下架商品 | 管理员 |
| SKU | `GET /admin/products/{id}/skus`、`POST /admin/products/{id}/skus` | 查询、新增规格；新增传 `specs, price` | 管理员 |
| SKU | `PATCH /admin/skus/{id}` | 修改规格、价格或上下架状态 | 管理员 |
| 购物车 | `POST /cart/items`、`GET /cart/items` | `skuId, quantity` 加入购物车，或查看自己的购物车 | 本人 |
| 购物车 | `PATCH /cart/items/{id}`、`DELETE /cart/items/{id}` | `quantity` 修改数量，或移除一项 | 本人 |
| 订单 | `POST /orders/preview` | `cartItemIds, addressId`，返回结算明细和总额，不创建订单 | 本人 |
| 订单 | `POST /orders` | `cartItemIds, addressId, requestId`，创建订单，返回编号、金额和状态 | 本人 |
| 订单 | `GET /orders`、`GET /orders/{orderNo}` | 分页查看自己的订单列表、详情 | 本人 |
| 订单 | `POST /orders/{orderNo}/cancel` | 取消待支付订单 | 本人 |
| 订单 | `GET /admin/orders`、`GET /admin/orders/{orderNo}` | 按编号或状态分页查询订单、查看详情 | 管理员 |
| mock 支付 | `POST /orders/{orderNo}/payments` | `result` 为 `SUCCESS` 或 `FAILURE`，返回模拟支付记录 | 本人 |
| mock 支付 | `GET /orders/{orderNo}/payments` | 查询该订单的模拟支付记录 | 本人 |

鉴权约定：管理员通过初始化脚本或受控配置创建，不接受注册参数自行提权，本轮不要求角色管理后台或多设备会话管理。Access Token 短期有效，Refresh Token 有效期更长；刷新返回新的双 Token，旧 Refresh Token 立即失效。退出使当前登录的两种 Token 失效；过期、已退出或已使用的刷新凭据不能再次续期。服务端同时校验角色权限和资源归属，有效期与失效方案写入 README。

例如，`POST /orders` 的请求体可以是：

```json
{
  "cartItemIds": [11, 12],
  "addressId": 3,
  "requestId": "checkout-20261102-001"
}
```

创建成功时返回订单编号、`PENDING_PAYMENT` 状态和服务端计算的总金额；单价、小计、总额和收货信息在订单详情中返回。相同用户携带相同 `requestId` 重试同一请求时，返回同一订单，不重复创建；同一标识用于不同请求内容时明确拒绝。新的一次购买使用新的标识。

例如，购买两件 39 元文化衫和一个 12 元徽章，创建订单的响应可以是：

```json
{
  "orderNo": "202611020001",
  "status": "PENDING_PAYMENT",
  "totalAmount": "90.00"
}
```

此例金额单位为元，使用十进制字符串；也可统一使用整数分，在接口文档中注明。订单状态可使用 `PENDING_PAYMENT`、`PAID`、`CANCELLED`；mock 支付请求示例为 `{"result": "SUCCESS"}`。

接口正常响应与错误响应的结构自行统一，在 Apifox 中给出示例。至少区分参数错误、未登录或令牌失效、权限不足、资源不存在和业务状态冲突，可分别使用 HTTP 400、401、403、404、409；不得用成功响应掩盖失败，也不要通过错误信息泄露其他用户的数据。

## 业务规则与测试

继续沿用前两轮的测试与异常处理要求，自动化测试需要断言结果，至少覆盖以下行为：

- 注册、登录、刷新、退出；错误密码、双 Token 过期、旧刷新凭据重用和退出后的访问；
- 普通用户调用管理接口，以及访问其他用户的地址、购物车、订单和支付记录；
- 类目、商品与 SKU 的维护和浏览；商品或 SKU 下架后不可加入购物车或下单，已有购物车项应提示不可购买；
- 数量为正整数、价格合法；同一 SKU 重复加入购物车时合并数量；只提交选中项，保留未选项；
- 预览和创建订单都由服务端读取当前商品状态与价格并计算金额，不信任客户端的用户编号、单价、总额或订单状态；预览不锁定价格，创建时重新校验可售状态并按当前价格计价，返回实际成交金额；
- 订单保存商品名称、规格、成交单价和收货信息快照，后续商品改名、改价或地址修改不改变历史订单；金额使用整数分或精确小数；
- 创建订单、明细和移除本次购物车项在同一本地事务中完成，任一步失败应完整回滚；重复提交不产生重复订单；
- mock 支付成功、失败后重试、重复支付，以及已支付或已取消订单的非法操作；同时支付与取消时只能得到合法结果。

另保留一次从管理员上架商品到用户选购、下单、模拟付款的接口调试记录，并验证取消另一笔订单和应用重启后的数据保留。失败时返回明确结果，日志保留排查信息，不泄露密码、Token 或内部错误细节。
