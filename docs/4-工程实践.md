# learn-backend 第四轮考核：完整电商与场景深入

## 项目描述

### 关于项目：小店开起来了，接下来做出自己的拿手好戏

上一轮，小店已经能展示商品、接收订单。这一轮要让它真正完成一笔生意：用户挑选商品、参加活动、下单付款，店主安排备货和发货，用户最后确认收货。取消或未付款的订单也需要有对应的处理，店主能查清商品、订单和货物的去向。

先串起完整交易链路，再选择一个场景深入，例如集中购买、热门商品详情、支付结果、商品搜索或发货进度。

本轮由**完整基础商城 + 一个自选专项**组成。基础商城限定为一家店、一个仓库、一种活动定价规则、一种本地模拟支付渠道和一条本地模拟发货流程。异步、重试、并发处理和压测必须落到真实业务链路中，可以分布在基础商城与专项里。

### 1. 六个业务域

本轮按以下六个业务域组织功能，其中支付属于交易域，选价属于活动域，库存属于仓储域：

| 业务域 | 项目中的功能 |
| --- | --- |
| 用户域 | 注册登录、个人信息、收货地址及用户身份 |
| 商品域 | 类目、商品、SKU、基础售价和上下架 |
| 交易域 | 购物车、订单、支付记录、取消与订单完成 |
| 活动域 | 活动配置、适用商品、活动价格、购买规则与选价 |
| 仓储域 | 默认仓库、SKU 库存、占用与释放、库存变化记录 |
| 履约域 | 履约单、模拟备货与发货、收货确认和处理进度 |

六个业务域用于划分职责，不对应六个独立部署的服务。

把它们串起来，就是：用户选定商品与规格，按适用活动确认价格，提交订单并占用库存，完成付款后进入备货与发货，最后确认收货；取消或超时未付款时结束订单并释放占用。用户、店主和后台工作围绕同一笔订单协作。

### 2. 活动与价格：这次周边有优惠

管理员可以创建、查看、修改和停用活动，设置名称、开始和结束时间、参加活动的 SKU 及价格规则。基础部分实现一种规则即可，例如指定 SKU 使用固定活动价；限量抢购、复杂优惠叠加等留给选择相关专项的同学。

用户在商品详情和购物车中能看到适用的活动信息与价格，订单展示商品原价、优惠金额和应付金额。活动开始、结束或停用后，商城展示相应的销售价格；未参加活动的商品仍按日常流程购买。

例如，“黑色 / M 码”文化衫原价 39 元，活动价 34 元；购买两件时，原价合计 78 元、优惠 10 元、应付 68 元。店主能够说明活动怎么卖，用户能够看清本次买了什么、花了多少钱。

### 3. 支付：订单终于可以付款了

为订单增加支付能力。用户提交订单后可以发起付款，查看付款是否完成；管理员或开发者通过本地模拟入口产生支付成功、失败或延迟返回的结果。

支付记录需要能够关联订单，展示金额、付款时间、处理状态和模拟渠道的流水信息。用户可以在订单详情中查看对应的支付进度，付款结果也应反映到订单状态中。

模拟支付提供发起付款、查询渠道结果和接收结果通知的完整交互，可以人为重复或延迟发送通知，也可以暂时不发送通知。它应当是一套可重复使用的本地模拟功能，不能只通过直接修改数据库演示“已付款”。

如果订单关闭后才收到付款成功，店主仍能查到付款与订单的对应关系，并通过模拟退款或带处理记录的人工流程完成处置。完整售后业务不在本轮范围内。

### 4. 仓库与库存：不能一直卖不存在的货

建立一个默认仓库，由管理员维护各 SKU 的库存，查询可售、已占用、已售等数量及库存变化记录。店主能够查清商品剩余多少，以及哪些订单正在占用或已经购买了这些货。

用户下单时占用本次购买所需的库存，付款完成后确认扣减；取消订单或超过约定时间仍未付款时，订单关闭，相关占用得到释放。库存不足时，用户能够知道本次购买未能完成。

例如，仓库中有 10 件文化衫，一个待付款订单购买 2 件后，其他用户还能购买剩余的 8 件。该订单取消后，这 2 件可以再次出售。

库存变化记录应能够查到关联订单、变动数量、时间和原因。采购、调拨和盘点不在本轮范围内。

### 5. 履约：把订单送到终点

订单正常完成付款、进入待发货阶段后，系统为其生成履约单。管理员可以查看待处理订单、模拟备货和发货；用户可以查询处理进度并确认收货。

履约记录包含关联订单、需要处理的商品、收货信息和当前状态。模拟物流提供发货请求与结果查询，成功后返回示例运单号，也能模拟暂时失败或迟迟没有返回结果。店主能够查到发货结果并继续处理失败的工作，不需要调用真实物流平台。收货完成后，订单也应反映已经完成的结果。

至此，用户能从商品浏览、参加活动、加入购物车、提交订单走到付款和订单完成，也能结束一笔尚未付款的订单。所有操作都在同一个项目中连贯运行。

### 6. 后台工作：稍后完成的事也要有结果

在上述业务中落地异步处理，例如付款后的履约任务生成、订单通知或超时未付款订单的关闭。至少完成一条与真实订单关联的后台链路，不能只提交独立的线程或消息队列示例。

管理员应能够查看后台工作的处理进度、尝试记录和失败原因。暂时失败的工作支持重试，持续失败的工作有可查询的记录和重新处理入口；应用重新启动后，仍能找到未完成的工作，用户能够查询业务的最终结果。

店主能按订单状态和时间查看待付款、待发货、已完成及待处理异常，并继续查到具体订单、库存变动和履约记录。使用管理接口或简单页面展示，报表平台不在本轮范围内。

运行中需要允许多个请求和多个后台任务同时执行。Java 方向应在实际功能中运用 JUC 的任务执行或并发协作能力；Go 方向使用对应的并发能力。任务执行方式、资源配置和消息组件由你结合项目决定。

### 7. 专项深入：选一件值得做深的事

基础商城跑通后，从下表选择一个场景深入。专项是必做内容，只完成所选方向。

| 可选场景 | 可以开发成什么 |
| --- | --- |
| 限量发售 / 秒杀 | 店主配置活动商品、发售数量和购买规则，用户集中参与购买并查询结果，成功后继续付款与收货；普通商品仍能正常销售。 |
| 支付结果处理 | 用户和店主能查清一笔付款的实际结果；结果迟到、暂时查不到或订单与渠道记录不一致时，有可追踪的处理进度和最终结果。 |
| 热门商品详情 | 大量用户集中浏览热门商品时，仍能及时看到可用的信息；店主修改商品或上下架后，用户看到的内容按约定更新，管理操作仍可使用。 |
| 商品搜索或推荐 | 二选一：让用户按关键词、筛选条件找到商品，或在一个推荐位发现商品；店主能调整展示规则，并用固定样例比较结果质量与响应速度。 |
| 发货时效与履约 | 为订单提供明确的发货承诺，店主能发现即将超时或已经超时的任务并处理，用户能查看预计时间、进度与异常后的安排。 |
| 活动选价与定价 | 选择一个价格场景，例如多活动下的价格选择，或基于模拟参考价格制定报价；店主能配置规则、预览结果，用户能看到明确的成交价。 |

也可以提出其他电商场景。开始前用一段话说明使用者、问题和改进目标，并与负责人确认工作量。涉及外部数据或服务时，使用固定数据、模拟行情或本地模拟接口。

专项必须接入自己的商城，使用已有商品、用户或订单等业务数据。其他业务域保持基础功能，深入改造所选链路。

说明场景中的主要使用者与访问特点，写清负载、资源条件、可用功能以及信息更新或业务处理的时间目标。模块、运行资源和数据组织方式自行设计。

项目 README 说明业务规则、关键流程、部署条件、容量目标和已知限制，保留必要的设计图、测试与运行记录。阅读和复用开源项目时注明来源、使用范围和自己的改动。

专项分析方法见[借助 AI 探索一个场景](架构阅读.md#借助-ai-探索一个场景)：先定位具体问题，再通过实现和实验验证方案。

### 8. 压测与改进：人多起来以后会怎样

对所选专项编写压测脚本，逐步增加负载，记录当前项目能承受的范围。说明测试数据如何准备、怎样判断一次操作完成，并保留相关日常操作作为对照。例如，商品详情专项可以同时安排浏览与管理端修改，支付专项可以安排付款请求与结果查询。选择符合场景的负载组合，不统一套用秒杀流量。

压测记录至少包括：

- 应用、数据库、消息组件和压测端的运行环境、资源配置及版本；
- 测试数据规模、请求速率或并发量、持续时间及业务结果；
- 吞吐量、P95/P99 延迟、技术错误与超时，并区分正常业务结果或拒绝；
- CPU、内存和所选链路涉及的连接等待、任务积压等运行情况。

如果请求先被接收、稍后才完成，需分别记录接收响应和最终业务完成情况。通过日志或指标找到一个具体瓶颈，完成有依据的修改，再在相同条件下复测。保留脚本、原始结果和改进记录，说明哪些变化有效、哪些问题仍未解决。

专项有自己的业务目标时，还需记录对应结果，例如搜索的固定样例效果、付款结果确认耗时或模拟订单的按时发货情况。速度变化与业务结果一起说明，并记录优化增加的资源开销。

同时为这条链路构造可重复的失败场景，例如模拟支付通知延迟、后台任务暂时失败或处理进程重启，观察失败与恢复过程。自动化测试继续覆盖功能及异常行为，优化后重新检查已有商城功能。

本轮不设统一 QPS 门槛。根据机器、数据规模和业务操作制定性能目标，并用可重复的测试结果说明当前容量。

## 推荐技术栈与资料

继续在自己的商城仓库开发并提交本轮 Git 标签或 Release。技术栈为推荐，优先使用当前最新正式版，关键适配明显不足时再调整，原则见[第 0 轮](0-开始之前.md)。Docker Compose 配置同步包含实际使用的组件，项目能按 README 初始化、启动、测试和运行压测。

| 用途 | Java 路线 | Go 路线 |
| --- | --- | --- |
| Web 与数据访问 | JDK 17+、Spring Boot 3.5.x，持久化框架使用兼容版本 | Hertz 或 go-zero，数据访问库使用兼容版本 |
| 并发与任务执行 | JUC：线程池、CompletableFuture、并发集合及同步工具，按实际需要选用 | goroutine、channel、context、sync |
| 异步消息（按需） | RabbitMQ 或当前项目适用的成熟消息组件 | RabbitMQ 或当前项目适用的成熟消息组件 |
| 缓存 | Redis，按专项需要使用 | Redis，按专项需要使用 |
| 自动化测试 | JUnit 与现有接口测试工具 | Go 标准测试工具、竞态检测 |
| 压测 | k6 或 JMeter | k6 或 JMeter |
| 运行诊断 | JDK Flight Recorder、应用日志和指标 | pprof、应用日志和指标 |

以下资料按实际问题查阅：

- [Java 并发工具包官方文档](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/package-summary.html)：当前 Spring Boot 路线的 JUC 参考入口，使用其他 JDK 时切换到对应版本。
- [RabbitMQ Reliability Guide](https://www.rabbitmq.com/docs/reliability)：消息处理与故障相关的官方说明。
- [Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)：AWS 关于重试与接口设计的工程文章。
- [Grafana k6 文档](https://grafana.com/docs/k6/latest/)：负载脚本、指标和运行结果的参考。

架构文章、开源实现和 AI 探索示例集中在[架构阅读](架构阅读.md)，用于比较方案；最终设计以项目问题和实验结果为依据。
